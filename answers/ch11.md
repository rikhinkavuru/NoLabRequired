# Chapter 11. Variables, strings, and DNA

Both exercises run on the `brca1` variable built at the top of Chapter 11, which
holds the first 200 bases of `NM_007294.4`.

## Exercise 11.1

**Goal.** Work out the GC content of the first 40 bases by hand, write it down,
then run the code.

**Answer.** Four numbers.

| | |
|---|---|
| G by hand | 17 |
| C by hand | 8 |
| Fraction by hand | 25 / 40 = 0.625 |
| Fraction Python prints | 0.625 |

The window, so you can recount it:

```
GCTGAGACTTCCTGGACGGGGGACAGGCTGTGGGGTTTCT
```

The code:

```python
window = brca1[0:40]
gc = window.count("G") + window.count("C")
print(window.count("G"), window.count("C"), gc, gc / len(window))
```

```
17 8 25 0.625
```

Both invariants hold. Tally the other two bases and you get A = 5 and T = 10, so
5 + 8 + 17 + 10 = 40. And 0.625 is a whole multiple of 0.025, which it has to be
when the denominator is 40.

**Why it comes out higher than 0.49.** The 0.49 was measured across all 200
bases, and this window is the first fifth of them. The start codon sits at
transcript base 114, so this window sits entirely ahead of the coding sequence,
in the untranslated front end. GC isn't spread evenly, even across 200 bases, and
Chapter 12 slides a window down the whole transcript and finds the richest 100
bases a long way past the middle.

**The most common wrong answer.** 0.6, from 24 over 40, which is exactly one
base short. Two runs in that window eat a G: `ACGGGGGACAGG` has five G characters
in a row, and `GTGGGGTTTCT` has four. Counting a run of five by eye and getting
four is what the check's 0.025 rule catches, because every correct answer is
a multiple of 0.025 and being out by exactly one step means you missed exactly
one base.

The second most common is running the code first and then writing the hand count
to match. Nothing stops you and nothing finds out. What you lose is the only
thing the exercise measures, which is whether your hand count and the machine's
agree when neither one has seen the other.

## Exercise 11.2

**Goal.** Extract the second exon of `NM_007294.4`, converting the record's
`95..193` into a Python slice.

**Answer.** One string and one number.

```python
exon2 = brca1[94:193]
print(exon2)
print(len(exon2))
```

```
TTCATTGGAACAGAAAGAAATGGATTTATCTGCTCTTCGCGTTGAAGAAGTACAAAATGTCATTAATGCTATGCAGAAAATCTTAGAGTGTCCCATCTG
99
```

The conversion is rule 2 from the chapter, applied one end at a time. The start,
95, is a 1-based position, so it becomes the Python index 94. The stop, 193,
doesn't move, because a Python slice stops before the index you hand it and gap
number 193 sits immediately after letter 193.

Both length checks agree:

```
193 - 95 + 1 = 99      (the record's arithmetic)
193 - 94     = 99      (Python's arithmetic)
```

And the second check, which is the one that catches an error in either
direction:

```python
print(exon2[114 - 95:114 - 95 + 3])
```

```
ATG
```

Transcript base 114 is where the coding sequence starts, and 114 falls inside
this exon, so the start codon has to appear at index 114 minus 95, which is 19.
It does.

**Why one end moves and the other doesn't.** Python numbers the gaps between
letters and starts at the gap in front of the first letter. A database numbers
the letters and starts at 1. Converting the start therefore costs you a
subtraction. Converting the stop costs you nothing, because writing gap number
193 as the end of a slice takes letter 193 with you instead of cutting it off.
The rule looks lopsided and it's the gaps, not a special case.

**The most common wrong answer.** `brca1[95:193]`, which is 98 characters long
and whose `ATG` sits at index 18 rather than 19. It comes from converting
neither end, on the reading that 95 and 193 are already numbers Python can use.
They are. They're legal indices, they name real letters, and both of the letters
they name are one place to the right of the ones you meant. Nothing errors.

The second is `brca1[94:192]`, also 98 characters, from converting both ends by
subtracting one from each. The `ATG` check still passes on this one, because the
error is at the far end and the start codon is near the front. Only the length
catches it. That's worth sitting with: one of the two checks in the check
misses this error entirely, which is why the box asks for both.

The third is doing the conversion once, at the end, with a single adjustment
meant to fix the pair. Do the two ends separately and check each one. They move
by different amounts because they mean different things.
