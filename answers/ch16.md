# Chapter 16. Reading errors

## Exercise 16.1

**Goal.** Diagnose and fix five broken scripts, committing to the error class in
writing before changing anything.

**The fixed scripts already exist.** One per broken script, in
`scripts/solutions/`, and each carries its diagnosis in the header comment,
including what the machine believed at the moment it stopped.

| Broken | Fixed |
|---|---|
| `scripts/broken/broken_1.py` | `scripts/solutions/broken_1_fixed.py` |
| `scripts/broken/broken_2.py` | `scripts/solutions/broken_2_fixed.py` |
| `scripts/broken/broken_3.py` | `scripts/solutions/broken_3_fixed.py` |
| `scripts/broken/broken_4.py` | `scripts/solutions/broken_4_fixed.py` |
| `scripts/broken/broken_5.py` | `scripts/solutions/broken_5_fixed.py` |

Read those for the fix and the reasoning. What follows is the diagnosis table the
exercise asks for, plus the output each fixed script prints.

## The diagnosis table

| Script | Error class | Last line, verbatim | What the machine believed |
|---|---|---|---|
| 1 | `SyntaxError` | `SyntaxError: '(' was never closed` | Two brackets were opened and one was closed, so the instruction never ended. Nothing in the file ran. |
| 2 | `NameError` | `NameError: name 'sequnce' is not defined. Did you mean: 'sequences'?` | It reached a name it had never been given a value for. The dictionary was built as `sequences` and used as `sequnce`. |
| 3 | `TypeError` | `TypeError: not all arguments converted during string formatting` | `reported_length` was text, and `%` with text on the left is old-style string formatting rather than remainder. It was formatting `"39"` and ran out of placeholders for the 3. |
| 4 | `IndexError` | `IndexError: list index out of range` | There are 13 codons at positions 0 through 12, and position 13 was asked for. |
| 5 | `KeyError` | `KeyError: 'CTT'` | The codon `CTT` appears in the sequence and has no entry in the table, which holds eight codons where the real genetic code has 64. |

All five class names are different, which is the check's first test.

## What each fixed script prints

```
broken_1_fixed.py   GC content: 0.359
broken_2_fixed.py   BRCA1_human 51
                    Brca1_mouse 51
broken_3_fixed.py   complete codons: 13
                    bases left over: 0
broken_4_fixed.py   number of codons: 13
                    last codon: AAT
broken_5_fixed.py   protein: MDLSALRVE
```

Those 39 bases in scripts 1, 3 and 4 are the opening of the *BRCA1* coding
sequence, from base 114 of `NM_007294.4`. 39 divides by three, so there are 13
whole codons and nothing left over. Script 3's check is that the length the file
claims and the length of the string agree.

## The reasoning worth carrying

**Read the last line first.** Every one of those five diagnoses came off the last
line of the traceback and nothing else. The class name says what kind of thing
went wrong and the message says which value it went wrong on. The frames above
say where the machine gave up, which is downstream of wherever you were careless.
In Chapter 16's worked example the mistake is on line 13 and the traceback stops
on line 2, and that gap is the normal case.

**Two of the five have a message that misdirects you.**

- Script 1's `SyntaxError` names line 10, which is where the bracket was
  *opened*. You'll be staring at line 12 wondering what's wrong with it.
- Script 3 complains about string formatting while you were trying to divide.
  That's the intended surprise, and `%` doing two unrelated jobs is the whole
  explanation.

**Script 1 has two places the bracket could go, and one of them is wrong.** Put
it after `len(sequence)` and you get:

```
gc_fraction = (g_count + c_count / len(sequence))
```

which runs cleanly and prints `GC content: 8.1538`. That's 8 plus 6 divided by
39, so the division happened before the addition. A GC content is a fraction of a
sequence and cannot be greater than 1, so 8.1538 is not a fraction of anything.
Fixing a `SyntaxError` in the place that makes the red text stop is not the same
as fixing it in the place that makes the answer right, and only the second one is
checkable.

## The most common wrong answers

**Two matching class names.** If two of your five agree, one is wrong. The pair
that collides most is scripts 2 and 5, both written down as `KeyError`, because
both involve a lookup that failed. Script 2 fails on the *name of the
dictionary*, before any lookup happens, so it's a `NameError`. Read the last line
of each again: one quotes `'sequnce'` and one quotes `'CTT'`, and the quoted
thing tells you which side of the lookup broke.

**Script 3 written down as a `ValueError`.** The reasoning is that a string
divided by a number should be a value problem. Python never got as far as
dividing. It read `%` between text and a number as a formatting instruction, so
the class is `TypeError` and the message is about formatting.

**Script 5 fixed with `.get(codon, "X")`.** It stops the error, the loop
finishes, and the protein comes back with an `X` in it. That's the trap from
the `KeyError` section arriving in your own code. A default is correct where a
missing key is expected and means something. Here the table was genuinely
incomplete, so the fix is to add the missing entry. Reaching for a default
converts a loud failure into a quiet wrong answer. `broken_5_fixed.py` adds the
entry and then raises on any codon still missing, which is the pattern to copy.

**Fixing before predicting.** The exercise asks you to write the class down
before you change anything, and skipping that step is free until it isn't. A
wrong prediction is worth more than a right one here, because it points at the
exact thing you believed that isn't true. There's no way to get that value back
after you've read the fix.
