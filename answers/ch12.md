## Exercise 12.1

**Goal.** Find every ATG in the transcript and print each one in both coordinate
systems.

**Answer.** 140 lines, ascending, two numbers on each.

```python
for i in range(len(brca1) - 2):
    if brca1[i:i + 3] == "ATG":
        print(i, i + 1)
```

The first ten lines:

```
113 114
150 151
159 160
164 165
254 255
301 302
309 310
414 415
471 472
494 495
```

The last line is `7040 7041`. The line count is 140.

Two numbers to keep from the same loop, because Chapter 13 checks against them.
Stepping through the coding range in threes instead of walking every position
gives 30 in-frame ATGs:

```python
count = 0
for i in range(113, 5705, 3):
    if brca1[i:i + 3] == "ATG":
        count = count + 1
print(count)
```

```
30
```

**Why the loop stops two short.** `range(len(brca1) - 2)` ends at index 7,085,
and `brca1[7085:7088]` is the last three-base slice the string can produce. Run
to `len(brca1)` and the last two passes ask for slices with one and two bases in
them, which can never equal `"ATG"`, so nothing errors and nothing changes. Run
past it and you get an `IndexError`. The count is what tells you which happened.

**Why 114 has to appear in the right-hand column.** It's where the coding
sequence starts, and Chapter 5 read that number off the database rather than out
of your code. Two independent routes to one number is the strongest evidence
available with nobody to ask. Your left column is Python's own count and your
right column is what a database would print.

**The most common wrong answer.** A right-hand column starting at 113, from
printing `i` twice. It reads fine, both columns are full of plausible numbers,
and the only thing that catches it is knowing that 114 belongs there.

The second is a right-hand column starting at 115, from converting twice: adding
one to a value that was already converted somewhere upstream.

The third is a count that isn't 140. Anything else means the `range` stopped in
the wrong place, and 138 is the usual value, from a loop that ended at
`len(brca1) - 4` or similar. Count your lines. The exercise gives you the number
so that a line count is a check rather than a curiosity.

## Exercise 12.2

**Goal.** Slide a window along the transcript, work out the GC content of each
window, and report the richest one, at two window sizes.

**Answer.** Two rows, plus the prediction you wrote first.

| Window size | 1-based start of the best window | GC fraction |
|---|---|---|
| 100 | 5,598 | 0.61 |
| 500 | 5,316 | 0.54 |

```python
for size in (100, 500):
    best = -1
    best_start = 0
    for start in range(len(brca1) - size + 1):
        window = brca1[start:start + size]
        gc = window.count("G") + window.count("C")
        if gc > best:
            best = gc
            best_start = start
    print(size, best_start + 1, round(best / size, 2))
```

```
100 5598 0.61
500 5316 0.54
```

The raw counts behind those fractions are 61 of 100 and 271 of 500.

**The prediction, and what actually happens.** The prediction the exercise wants
has two parts, and both are directions rather than numbers.

- *What happens to the GC fraction when the window grows?* It falls, 0.61 down
  to 0.54. It has to. A 500-base window is five 100-base windows averaged
  together, and an average of five things can't beat the best of the five. That's
  the invariant in the check, and it holds for any sequence, so a longer
  window scoring higher means an arithmetic bug rather than a discovery.
- *What happens to where you find it?* It moves, 5,598 back to 5,316, and it
  doesn't have to. The 500-base window is centered on roughly the same GC-rich
  region and starts earlier because it has to reach further to cover it. Nothing
  guarantees the two windows land near each other, and on a transcript with two
  separate GC-rich patches they wouldn't.

Both windows sit past the middle of the transcript, a long way from the
GC-rich front end that Exercise 11.1 measured at 0.625 across 40 bases. A 40-base
window will always beat a 100-base one for the same reason a 100 beats a 500. The
window size is part of the answer, and a GC number with no window size attached
doesn't mean anything.

**The most common wrong answer.** Reporting 5,597 and 5,315, which are the
Python indices. The exercise asks for the 1-based start, so add one on the way
out. This is the same conversion as Exercise 12.1's right-hand column, arriving
in a place where there's no check number waiting to catch it.

The second most common is a correct fraction with a start further along the
transcript. That means you kept the last tied window instead of the first.
Several windows tie for the top score, and `if gc >= best` overwrites the record
holder on every tie while `if gc > best` keeps the first one you met. Changing
`>=` back to `>` moves the answer back.

The third is walking the windows in steps instead of at every position. Chapter
12's walkthrough used `range(0, 500, 100)` for a printable example, and copying
that step of 100 into this exercise means you tested 71 windows out of 6,989.
The exercise says a window starting at every position in turn.
