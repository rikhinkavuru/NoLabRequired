# Chapter 24. Everything ran, and the answer came out backwards

Both exercises start from the chapter's own state: `counts`, `samples` joined by
key, `kept`, `logcpm`, and the `compare` and `pick` functions.

## Exercise 24.1

**Goal.** Run the stage comparison inside the luminal samples instead of the
basal ones, and report what happens to *Brca1*.

**Answer.** Three numbers.

| | |
|---|---|
| Genes tested | 14,173 |
| With an adjusted p-value below 0.05 | 10,951 |
| *Brca1* log2 fold change | -0.08 |

```python
by_luminal = compare(pick("luminal", "virgin"), pick("luminal", "lactating"))

print(len(by_luminal), "genes tested")
print((by_luminal["p_adjusted"] < 0.05).sum(), "with adjusted p below 0.05")
print(by_luminal.loc[12189, "log2_fold_change"].round(2))
```

```
14173 genes tested
10951 with adjusted p below 0.05
-0.08
```

*Brca1*'s raw p-value in that comparison is 0.696 and its adjusted p-value is
0.710. It isn't close to anything.

**Where the missing 37 genes went.** 14,210 minus 14,173 is 37. Those 37 have
identical values inside both luminal pairs, so the t-test had nothing to divide
by and returned `NaN`, and the `dropna` line in `compare` sets them aside. The
basal comparison lost 4 the same way. Different pairs of samples, different
constant genes.

**Why 10,951 against the basal comparison's 9.** Two samples per group in both
cases, so it isn't sample size. Luminal cells are the ones that make the milk, and
they rebuild themselves across lactation, so the real differences between a virgin
luminal sample and a lactating one are enormous and consistent. Basal cells change
far less. Chapter 24's own correlation block measures it: the spread of stage fold
changes is 1.18 in luminal cells against 0.77 in basal ones, and the two effects
correlate at only 0.23. Same tissue, same stages, two nearly unrelated answers.

**What *Brca1* at -0.08 means for the chapter's argument.** It moves in basal
cells across these stages, from a log2 fold change of -2.29, and it barely moves
in luminal ones. Pool the two cell types together and the pooled effect tracks the
luminal one at 0.87, so a pooled analysis would have reported *Brca1* as roughly
flat across lactation. That's the whole reason the two cell types had to be
separated, and the results table has no column anywhere saying which half of the
tissue a number came from.

**The most common wrong answer.** 14,210 genes tested, because that's the number
of rows in `logcpm` and the number the chapter prints for the basal-against-luminal
run. The count depends on which samples you compared, since a gene with no
variation inside either group of *this* comparison drops out of *this* table.
Print `len()` on the table you built rather than carrying a number over.

The second is a `p_adjusted` column that's entirely `NaN`, which returns 0 for
every threshold count and no error. A single `NaN` p-value propagates backwards
through `np.minimum.accumulate` and wipes out all 14,210 values. Check with
`print(table['p_value'].isna().sum())`. If that's above zero, you're missing the
`dropna` line in `compare`.

## Exercise 24.2

**Goal.** Predict, then run. Skip the low-count filter, build `logcpm_all` from
all 27,179 rows, and redo the basal virgin against lactating comparison.

**Answer.** Two numbers and one sentence.

| | With the filter | Without it |
|---|---|---|
| Genes tested | 14,206 | **20,047** |
| Adjusted p below 0.05 | 9 | **536** |

```python
logcpm_all = np.log2(counts / counts.sum() * 1e6 + 1)
by_stage_all = compare(pick("basal", "virgin"), pick("basal", "lactating"),
                       table=logcpm_all)

print(len(by_stage_all), "genes tested")
print((by_stage_all["p_adjusted"] < 0.05).sum(), "with adjusted p below 0.05")
```

```
20047 genes tested
536 with adjusted p below 0.05
```

27,179 minus 20,047 is 7,132 rows that never got tested at all, because they have
no variation inside either group and `dropna` set them aside.

**The sentence: why the count moved the way it did.** It went up, and the
prediction the exercise pushes you toward is that it should go down. Benjamini and
Hochberg multiply each p-value by the number of tests, and you ran 5,841 more of
them, so survival should get harder. What overwhelms that is where the extra rows
come from. They're genes sitting at a handful of reads, and with two samples per
group a pair of tiny counts that land identical or nearly so gives a tiny spread.
A t-test divides the difference between the group means by that spread, so a tiny
spread gives a tiny p-value no matter how few reads are behind it. The filter's
job is to remove rows a t-test can't read honestly, and taking it away hands you
536 hits where 9 was the honest number.

**Why the prediction is worth writing down first.** Nearly everybody predicts the
count falls, and the reasoning behind that prediction is correct as far as it
goes. What it misses is that the correction is arithmetic on the p-values and the
p-values themselves are what the filter was protecting. You can't get that
realization back after reading the answer, which is why the exercise says to
commit to a number first.

**The most common wrong answer.** Getting 27,179 tested. That means your `dropna`
line isn't running or your `compare` is a different function from the chapter's.
20,047 is the count after 7,132 constant rows fall out. The gap between those two
numbers is itself worth a note: more than a quarter of the rows in this file can't
be tested at two samples a side.

The second is running `logcpm_all` off `kept` rather than off `counts`. The
exercise says all 27,179 rows, and `kept` is already the filtered 14,210. The tell
is that your tested count comes back 14,206 again, exactly matching the filtered
run.

The third is normalizing before rather than after dropping the filter, meaning you
divided by `kept.sum()` while indexing `counts`. Library sizes computed off the
filtered matrix differ from library sizes computed off the whole one, so every CPM
shifts slightly. It doesn't change the headline here and it will bite you
somewhere else. Divide each column by its own total, from the same table you're
dividing.
